# Design Decisions

Format for each entry: decision, alternatives considered, reasoning. Newest at the bottom.

---

### D1. Write a custom UFCStats scraper instead of using an existing Kaggle dataset
- **Alternatives:** Kaggle fighter-statistics datasets and their scrapers.
- **Why:** Those datasets are one row per fighter with career aggregates as of the scrape date. Training on them leaks the future: a 2019 fight would see 2026 stats. The model needs per-fight data so features can be rebuilt as of each fight date.

### D2. SQLite for storage, S3 for published artifacts
- **Alternatives:** PostgreSQL (managed), DynamoDB, plain files.
- **Why:** A few thousand bouts written by one batch job at a time. SQLite has no server and no monthly cost. Managed Postgres would cost money every month to store a few megabytes. Published predictions are static JSON in S3 because page views only read.

### D3. Precompute predictions in batch
- **Alternatives:** an always-on inference API.
- **Why:** Predictions only change when cards or the model change. Batch publishing makes page views nearly free and removes a running server.

### D4. Manual model promotion
- **Alternatives:** automatic retraining and deployment after every event.
- **Why:** Automatic promotion can ship regressions or bad data silently. A registry plus a manually edited `approved.json` pointer keeps promotion deliberate and rollback trivial.

### D5. Corner is never a feature; train on both orientations
- **Alternatives:** keep red/blue as given.
- **Why:** The red corner is usually the favorite or champion, so corner leaks information and makes predictions depend on arbitrary labeling. Difference features, both-orientation training, and averaged inference make outputs symmetric by construction.

### D6. Chronological splits, log loss as the selection metric
- **Alternatives:** random splits, accuracy.
- **Why:** Random splits let the model train on fights after the ones it is tested on. Log loss rewards calibrated probabilities, which matter more for a probability product than raw accuracy.

### D7. Stats-only headline model; odds evaluated separately
- **Alternatives:** odds as a primary input.
- **Why:** Odds would likely dominate a model and make it copy the market. Keeping the headline model stats-only preserves the question of whether it knows something the market does not. A blended model is evaluated separately once odds data exists.

### D8. All history for features, recency-weighted training
- **Alternatives:** cut data at a recent year.
- **Why:** Features need full history (a fighter's 2015 features depend on 2008 fights). The sport has changed, so recent fights get more training weight; the decay rate is chosen on validation.

### D9. Debuting fighters are predicted and labeled
- **Alternatives:** skip their bouts; source pre-UFC records.
- **Why:** Most cards include a debut, and skipping them leaves cards half empty. Stats are marked missing (not zero), the UI labels these bouts "limited data," and their accuracy is reported separately. Pre-UFC records are a later extension.

### D10. Style archetypes use soft clustering and percentiles
- **Alternatives:** hand-assigned tags; k-means with distance-to-centroid as a skill score.
- **Why:** Hand tags are subjective and cannot be reconstructed historically. Distance to a centroid measures how typical a fighter is, not how good: the most extreme power puncher sits far from the center. Gaussian mixtures capture hybrid styles as probabilities; percentiles within weight class measure strength.

### D11. Anthropic API with prepaid credits for the analyst
- **Alternatives:** Amazon Bedrock.
- **Why:** AWS bills after the fact, so caps must be built in the app. Prepaid credits with auto-reload off are a true hard ceiling. A provider interface keeps a later switch to Bedrock simple.

### D12. Development inside WSL2 on ARM64
- **Alternatives:** native Windows.
- **Why:** The development laptop's Smart App Control blocks unsigned compiled extensions in Windows virtual environments, which previously caused silent test failures. Linux aarch64 is better supported by the ML stack.

### D13. Do not solve or work around the UFCStats bot challenge
- **Context:** On 2026-11-16 every UFCStats page, including the events list, returned a "Checking your browser" page that requires running a JavaScript proof-of-work and posting the answer before content is served. `robots.txt` returns 404, so there are no robots rules either way.
- **Alternatives:** solve the proof-of-work in the HTTP client (technically easy); drive a headless browser; present a browser User-Agent.
- **Why:** The challenge is the operator's signal that automated clients are not wanted. Defeating it would be circumventing an access control, and a public portfolio repository that does so loses the credibility it is meant to build. This is a standing rule for the project, not a temporary choice: no code here requests ufcstats.com at all. UFCStats URLs in the data are parsed for their IDs only.

### D14. Ingest a published per-round dataset instead of scraping (replaces the method of D1)
- **Alternatives:** a licensed feed such as Sportradar (clean on terms, unlikely to fit a $5/month budget); asking the operator for access (slow, no guarantee); waiting to see if the challenge is temporary; Kaggle fighter-level datasets (rejected in D1 and still rejected).
- **Why:** `Greco1899/scrape_ufc_stats` publishes six CSVs collected from UFCStats and refreshes them with a daily scheduled job. D1's requirement still holds and is met: the data is one row per fighter per round of each fight, with no career aggregates, so features can be rebuilt as of any fight date. Checked before building on it (commit `96adace`, 2026-11-15): most recent event 2026-11-14; events, fights and fighter profiles carry UFCStats URLs; licence GPL-3.0.
- **Costs accepted:** fights name their fighters as text, not IDs (D17). The dataset starts at UFC 2; UFC 1 is absent. Fighter profiles are captured once and not refreshed, so height and reach are often empty for recent debutants (M2 will quantify this). The project now depends on one volunteer-run feed that could stop; snapshots are pinned to a commit and the last good database is never overwritten by a failed load, so a stoppage freezes the data rather than breaking the site.

### D15. Terms-of-use caveat, stated plainly
- **What is known:** The dataset is itself a scrape of ufcstats.com. UFC.com's terms of use prohibit automated access, scraping, and compiling site content into a database, and say they cover Zuffa's associated sites; ufcstats.com is not named in them, so whether they apply is unclear. UFCStats's own terms could not be read because its pages are behind the challenge. Upstream's published code uses plain HTTP requests with no challenge handling; how it still collects data is not known to us.
- **What this means:** Downloading the CSVs from GitHub means this project makes no requests to UFCStats, but it does not settle whether the data may be used. Upstream's GPL-3.0 licence covers its repository; it cannot grant rights the data's owner has not given. This project uses the data for a non-commercial portfolio and commits none of it. Earlier commits included two small excerpts (29 fights and 4 fights under `tests/fixtures/`); they were removed from the working tree on 2026-11-16 and remain in git history only. Test fixtures are now synthetic: `scripts/make_synthetic_fixtures.py` writes invented fighters, events and statistics in the real column layout and covers the same edge cases. The one test that needs real rows, the hand-calculated spot check, reads them at test time from the git-ignored snapshot in `data/external/greco/` and is skipped, with the reason, when the snapshot is absent. The shipped `identity_overrides.csv` holds fighter names, IDs and short notes of evidence; it is configuration for the real snapshot, not an excerpt of its rows.
- **Consequences:** Commercial use stays a non-goal until licensing is resolved (see SPEC). If the operator or upstream objects, the source is swapped behind `src/ufc/ingest/`; nothing downstream reads the CSVs directly. The methodology page must say where the data comes from and repeat this caveat.

### D16. Wikipedia for upcoming cards
- **Alternatives:** UFCStats upcoming-event pages (blocked, D13); ufc.com event pages (its terms prohibit automated access outright); a paid schedule API.
- **Why:** The dataset has completed events only. Wikipedia's MediaWiki API is meant for programmatic use, its content is CC BY-SA, and event pages list bouts in a regular template (`{{MMAevent bout|weight class|fighter|vs.|fighter}}`). Confirmed on a live upcoming event; responses saved in `tests/fixtures/wikipedia/`.
- **Costs accepted:** Wikipedia is edited by volunteers and can be wrong, late, or vandalised, so M5's validation gate has to treat a card as untrusted input. It has no UFCStats IDs: upcoming bouts need their own IDs, and fighter names (with diacritics and disambiguation suffixes) go through the same name resolution as D17. The site must attribute Wikipedia.

### D17. Resolve fighter names to IDs with exact rules and explicit overrides; never fuzzy matching
- **Context:** Fighter profiles have IDs, but a fight row only names its two fighters. Some names in the snapshot belong to two profiles each (for example two fighters called Bruno Silva), and bout rows sometimes spell a name differently from the profile. At commit `96adace` the load reports 56 fighter names resolved by weight class or override.
- **Rule, in order:** an entry in `identity_overrides.csv`; a name (ignoring case, accents and punctuation) that belongs to exactly one profile, counting both the current listing name and the name recorded when the profile was first captured; for a shared name, the one profile whose listed weight fits the bout's weight class; otherwise unresolved.
- **Alternatives:** fuzzy string matching; picking the nearest weight; picking the most active fighter.
- **Why:** A wrong match silently gives one fighter another's history and corrupts every feature built on it. A reported gap is visible and fixable. Nearest-weight was rejected on evidence: for one lightweight bout it picks a profile born in 1977 with no other bouts over the active featherweight of the same name. Each override records the evidence from the dataset that justifies it, and every non-trivial resolution is written to `ingest_issues`. Two cross-checks pass on the full snapshot: no fighter is under 17 or over 55 at any bout, and no fighter appears in both a women's and a men's weight class.

### D18. Drop and report what cannot be joined with certainty; gate the load
- **Alternatives:** best-effort joins; loading partial rows with NULL fighters.
- **Why:** The files join on event name and bout text, which fails in known ways: a renamed event leaves fights listed twice (resolved: keep the row whose event exists), an event missing from the events file orphans its fights (dropped), and the same pairing fought twice on one card makes its stats rows indistinguishable (both bouts load, without stats). At commit `96adace`, 3 of 9,003 fights are dropped and all are listed by `uv run python -m ufc.ingest load --dry-run`. A dropped bout is missing from both fighters' histories, which is a small known error; a guessed one is an unknown error.
- **Gate:** if more than 1% of fights are dropped or the tables would be internally inconsistent, nothing is written. A broken upstream file therefore cannot replace a good database.

### D19. Store per-round stats and derive per-fight totals at load time
- **Alternatives:** store only totals; compute totals in a SQL view.
- **Why:** The source is per round, and rounds allow later features (pace, fading) without re-ingesting. Totals are summed in one tested Python function and stored, so readers get a plain table. Control time, which early events do not record, is NULL in the total if it is NULL in any round: a partial sum is never presented as a total. Bouts with no stats have `has_stats = 0` and no stats rows, never zeros.

### D20. Schema deviations from the original plan
- **raw_pages replaced by source_files:** there are no fetched pages any more. `source_files` records the upstream commit and a SHA-256 per CSV, which is what the model registry needs to name its training data.
- **ingest_issues added:** the validation report of the last load is queryable, so the data quality report and the methodology page can cite it.
- **bout_round_stats added:** see D19.
- **bouts gained** `bout_type_raw`, `is_interim_title`, `is_tournament_final`, `time_format`, `fight_time_s`, `method_details`, `referee`, `has_stats`. `is_title_bout` means a UFC championship bout, including interim titles and the 1990s superfight title. Tournament finals (early UFC tournaments, The Ultimate Fighter, Road to UFC) are flagged separately, because the source labels them "Title Bout" and counting them would inflate title-fight experience. `fight_time_s` is computed from the bout's format so per-minute rates do not have to re-derive round lengths, including the one-round-plus-overtime formats of the 1990s.
- **is_womens is partly inferred:** the source says "Women's" only inside a weight class name, so women's catch-weight bouts are unlabelled. A bout with no gendered class is marked women's if either fighter also appears in a women's weight class.
- **predictions deferred to M5:** upcoming bouts will come from Wikipedia without UFCStats IDs (D16), which changes what a prediction's bout key is. Defining the table now would mean redefining it.

### D21. Timestamps come from the snapshot, not the clock
- **Alternatives:** stamp rows with the time of the load.
- **Why:** `first_seen_at` and `last_seen_at` are set from the upstream commit date of the snapshot being loaded. Loading the same snapshot twice therefore produces byte-identical tables, which is what the idempotency test asserts, and the timestamps mean "when the data said this" rather than "when a job happened to run". They are merged with min and max, so loading snapshots out of order cannot move them the wrong way.

### D22. Fighter attributes are dropped when a profile's two names disagree
- **Context:** Upstream rewrites the fighter listing from the live site but captures height, reach, stance and date of birth once and never refreshes them. In four profiles the current name and the name the attributes were captured under share no word (for example a heavyweight listed with a 125 lbs weight and a 2004 birth date recorded under a woman's name).
- **Alternatives:** trust the attributes; drop the profile.
- **Why:** The attributes may belong to a different person, and age and reach are model features. The profile and its bouts are kept; the four attributes are left empty and a warning is recorded. More generally, leakage rule 3 in ML_REQUIREMENTS treats these attributes as static, and this source makes them static as of first capture, which is the same assumption with an earlier date.

### D23. Features are built one date at a time from append-only fighter histories
- **Decision:** Bouts are processed in date order. For each date, features for all of its bouts are computed first, and only then are those bouts added to the store and Elo advanced. A fighter's state is a list of his bouts with running sums of one vector of additive counts per bout (strikes landed and attempted, seconds fought, wins, and so on, for him and for his opponent). Every read goes through one lookup that returns the bouts strictly before a cutoff date. `build_matchup` uses that lookup to price any pair on any date, and the batch build calls the same function.
- **Alternatives:** a SQL query per bout with `WHERE date < ?`; recomputing each history from raw rows for every bout; grouping by event instead of date; separate code for training features and upcoming-bout features.
- **Why:** The date is the unit because the rule is "strictly before D" and five dates in the data hold two events. There are two independent guards against the same mistake: in the batch build later bouts are not in the store yet, and the lookup would exclude them even if they were. One function for training and prediction means the two cannot drift apart, and a test checks that asking the finished store about any past bout reproduces the batch row exactly. Running sums make a full rebuild take seconds, so the pipeline is simply rerun from scratch; there is no incremental state to corrupt.

### D24. Rates are pooled sums; missing values are NaN with two flags per fighter
- **Decision:** A rate is total numerator over total denominator across the bouts in a window (career, last 3 bouts, last 5 bouts, or time-decayed with a 730-day half-life fixed in advance). A bout without recorded stats adds nothing to either side, so a window with no recorded stats has a zero denominator and the rate is NaN. Two flags per fighter say why: `debut` (no earlier UFC bout) and `no_stats` (no earlier bout with recorded stats). Record counts such as bouts and wins are true zeros for a debutant; stat counts and rates are NaN.
- **Alternatives:** averaging per-fight rates; filling missing stats with zero or a league mean; shrinking every rate toward a prior.
- **Why:** Pooling is how the sport reports these stats, it weights a 25-minute fight more than a 20-second one, and it can be checked by hand (the spot-check test does). Zero-filling would tell the model a debutant has no offense and perfect durability. Imputation is a fitted step and belongs in M4, on training data only.
- **Costs accepted:** A fighter with very little cage time has extreme per-minute values, and a ratio with no attempts (never faced a takedown) is NaN without a flag of its own. The differences in bouts and cage minutes tell a model how much evidence stands behind a rate; clipping, if wanted, is a fitted M4 step.
- **Conventions:** doctor's stoppages count as KO/TKO; a no contest is left out of win rates and does not break a streak; windows count a fighter's most recent bouts of any kind. Height, reach, stance and date of birth are treated as static (leakage rule 3, D22); age is computed at the bout date.

### D25. Opponent-adjusted stats: actual minus expected, with opponents' baselines taken at the same cutoff
- **Decision:** For fighter F at cutoff D, each earlier bout of F with stats is compared with its opponent's baseline: the opponent's own totals over his bouts strictly before D, leaving out his bouts against F, plus two league-average bouts as a prior. The baseline gives a rate (for example, the share of takedown attempts opponents usually land on him), which times F's actual exposure in the bout gives an expected count. The adjusted stat is (actual - expected) / exposure over F's history, in career and time-decayed versions. Ten stats are adjusted, including the takedown-defense example in ML_REQUIREMENTS.
- **How the cutoff is respected:** F's bouts and every opponent's bouts are read through the same strictly-before-D lookup, so nothing on or after D is used on either side. The league-average prior is fitted on the training period only.
- **Alternatives:** freezing each opponent's baseline at the date he fought F; including the bouts against F in his baseline; a ratio instead of a difference; solving for all fighters' offense and defense ratings at once.
- **Why:** A baseline frozen at fight time throws away what the opponent did afterwards, which is legitimate evidence about how good he was and is still before D; it also leaves most early-career opponents with no baseline. Bouts against F are excluded because they would make F's own performance part of the yardstick it is measured against. Differences stay finite when an expected value is near zero. A simultaneous solve would have to be rerun for every date to stay as-of and is hard to explain; this method is two lookups and can be checked by hand.
- **Costs accepted:** An opponent's baseline is his whole record before D, so one who has since declined looks weaker than he was when they fought. The prior strength (two bouts) is a judgment, not tuned.

### D26. Elo: one update per date, parameters fitted on the training period
- **Decision:** All bouts on a date are scored against ratings from before that date, and the changes are applied together afterwards. Draws score one half; no contests are not rated. Three parameters are chosen by grid search to minimise the log loss of pre-fight predictions on bouts through 2022-12-31: the step K, a multiplier for finishes, and a multiplier for a fighter's first three rated bouts. The build prints the chosen values and the training log loss; on snapshot `96adace` they are K = 56, finish 1.15, early-career 1.5 (`uv run python -m ufc.features build`).
- **Alternatives:** a conventional fixed K of 32; separate ratings per weight class; Glicko; using judges' margins.
- **Why:** Updating per date keeps the one-night tournaments of the 1990s, where a fighter fought several times in an evening, from leaking one bout into the next. Each prediction in the fitting loss uses earlier dates only, so it is an honest one-step-ahead score. One rating across weight classes keeps fighters who change class connected. The fighter's own rating difference is included as a feature and grouped with opponent quality (family 8), since both come from this system.
- **Note for M4:** ML_REQUIREMENTS also says the Elo baseline's K is tuned on validation. The ratings used as features never see validation data; a validation-tuned baseline would be a separate run of the same code.
- **Detail:** each fighter's expected score is computed from his own side. Computing one as one minus the other differs in the last bit and made ratings depend on which fighter the source lists first; the symmetry tests caught it.

### D27. Fitted parameters are inputs to the build, and the leakage tests treat them that way
- **Context:** Two rules are in play. The as-of rule says a feature for date D uses only earlier bouts. The fit-on-training rule lets Elo parameters and league baselines use the whole training period. So a 2015 feature legitimately depends on parameters chosen with bouts through 2022, exactly as it would on a scaler fitted on the training set.
- **Decision:** The parameters are an explicit input (`FittedParams`), saved in `features_meta.json`. The perturbation test has two forms. With parameters held fixed, changing or deleting every bout after any date D leaves all features on or before D exactly equal. With fitting included, changing every bout after the training period changes neither the parameters nor any training-period feature. The same-event test changes or deletes the other bouts on a card and requires the bout's row to be exactly equal.
- **Alternatives:** refitting parameters at every date so that nothing ever depends on a later bout.
- **Why:** Refitting per date would make the same stat mean different things in different years and is not what rule 4 asks for. Comparisons are exact rather than approximate, so a leak of any size fails.

### D28. Every model feature is antisymmetric; style matchups are products
- **Decision:** Each feature is `f(A) - f(B)` for a per-fighter value, or `m(A, B) - m(B, A)` for a pair value, so swapping the fighters negates it exactly (tested with exact equality, and by rebuilding with every bout's listing order reversed). Style matchups multiply one fighter's offense by the other's weakness: takedowns per 15 minutes times the share of takedowns the opponent fails to stop, strike attempts per minute times the share of strikes he fails to avoid, knockdowns scored times knockdowns absorbed, control share times control conceded, submission attempts times his rate of submission losses. Stance is the two fighters' southpaw and switch indicators differenced, plus a signed southpaw-versus-orthodox term.
- **Alternatives:** sums such as "A's accuracy minus B's defense"; keeping both fighters' raw values as separate columns; a categorical stance pair.
- **Why:** The source lists the winner first far more often than not (the mean of `label` in the feature file shows it), so any trace of listing order would leak the result. A sum of one fighter's offense and the other's defense is only a combination of difference features that already exist; a product is new information. A categorical "orthodox vs southpaw" changes value when the fighters swap, which breaks exact symmetry; the signed term carries the same fact.
- **Costs accepted:** Differences drop the level: two 38-year-olds look the same as two 25-year-olds. Only weight class, the bout format and the per-fighter flags are kept undifferenced. If M4 shows level matters, symmetric features (sums) can be added without touching the antisymmetric ones.

### D29. Family 12: cardio as pooled rounds-3+ rates over round-1 rates
- **Decision:** From per-round stats, over a fighter's earlier bouts that reached round 3: significant strikes landed, attempted and absorbed per second in rounds 3 and later, each divided by the same rate in round 1 (career and time-decayed), plus the change in accuracy and in defense, and the number of such bouts. Rounds before the last ran their full scheduled length; the last ran to the recorded end time. A fighter with no bout past round 2 has NaN for all of these except the count.
- **Alternatives:** averaging per-bout ratios; log ratios; comparing round 2 as well; counting bouts that ended in round 2.
- **Why:** Sums are pooled across bouts before dividing, so one bout with nothing landed in round 1 does not produce a division by zero or a wild ratio by itself. A plain ratio handles "landed nothing late" as zero, where a log ratio is undefined. Round 2 is left out to keep the contrast between fresh and tired.
- **Costs accepted:** Missing for every fighter without a long bout. With a single qualifying bout the ratio is noisy and can be large; the count is provided so a model can discount it. The sample is selected: only bouts a fighter did not finish (or lose) early are measured.

### D30. M2: leave the three dropped bouts dropped; do not add an override for "Jose Montanha"
- **Context:** The load at commit `96adace` drops three bouts (`docs/DATA_QUALITY.md`). Two name an event that is absent from the events file. One names "Jose Montanha", shared by two profiles whose names are crossed between the details file and the tale-of-the-tape file.
- **Alternatives:** add an override pointing at the profile that two of three name signals favour; infer the missing event's date from neighbouring events; raise the gate so nothing is dropped.
- **Why:** An override must rest on evidence in the dataset, and here the dataset contradicts itself: the weight class fits both profiles, neither has another bout to cross-check, and the signals disagree. A wrong override gives a real fighter another's bout, which D17 rules out; a dropped bout is a visible, counted gap. The orphan-event bouts have no date anywhere in the data, and an override only maps fighter names, so it cannot help. The report's numbers come from `scripts/data_quality.py` and are regenerated into a marked block of the document, so the prose around it cannot drift into hand-typed metrics unnoticed.
- **Costs accepted:** one bout missing from two fighters' histories, and two Road to UFC bouts missing.

### D31. Own Elo is its own feature family (13, "rating")
- **Context:** D26 grouped the fighter's own rating difference with opponent quality (family 8) because both come from the Elo system. In the M3 review this was changed before any model was trained.
- **Alternatives:** leave `d_elo` in family 8.
- **Why:** The ablation removes one family at a time. With both in one family, removing it answers two questions at once: "does the model need a rating of the fighter" and "does it need to know whom he fought". They are different claims, and the first is likely the strongest single feature in the model. Family 8 now holds only opponents' ratings; family 13 holds `d_elo`. The feature itself and its column position did not change.

### D32. One Elo, fit on training; the baseline uses the same ratings (resolves the note in D26)
- **Context:** ML_REQUIREMENTS said two things: Elo parameters are fit on training only (leakage rule 4), and the Elo baseline's K is tuned on validation. D26 left the second for M4.
- **Decision:** The Elo parameters are fit on the training period only, and the Elo baseline is the win probability implied by the same as-of ratings that are stored as features. Nothing about Elo is tuned on validation. The Baselines text in ML_REQUIREMENTS was corrected.
- **Alternatives:** a second Elo run with K tuned on validation, used only as the baseline.
- **Why:** Two Elo systems would mean the baseline and the model's rating feature disagree about every fighter, and the comparison "model versus Elo" would no longer isolate what the other features add. Tuning K on validation would also give the baseline a look at the validation outcomes that the feature never gets. Ratings still move after 2022 as bouts are completed; only K and its multipliers are frozen.

### D33. Per-minute rates are shrunk toward the weight-class mean; the strength is chosen on validation
- **Context:** D24 accepted that a fighter with little cage time has extreme per-minute values: one knockdown in a 20-second fight is a rate of 45 knockdowns per 15 minutes. How heavy the tails are on the training period, before and after shrinkage, is tabulated in `docs/MODEL_REPORT.md`.
- **Decision:** Every rate over cage time (strikes landed, absorbed and attempted per minute, head strikes absorbed per minute, knockdowns scored and absorbed, takedowns and submission attempts per 15 minutes; career, last-3, last-5 and decayed) becomes `(count + m * class mean per minute) / (minutes + m)`. This is the empirical-Bayes estimate of a rate under a gamma prior worth `m` minutes at the class average. The count and minutes are the fighter's own, as of the cutoff. The class is that of the bout being predicted. `m` is one number for all rates, chosen on validation from a grid that includes 0; the grid, the criterion and the result are in `docs/MODEL_REPORT.md`.
- **Fitted on training only:** the class means are pooled counts over pooled minutes of training-period bouts. A class needs 50 training bouts with stats and a fixed weight limit to have its own mean; smaller classes and catch-weight or open-weight bouts use the mean over all bouts. The means are stored with the other fitted parameters in `features_meta.json`.
- **Details:** In the decayed window the prior counts as minutes fought on the cutoff date, so a fighter whose only bouts are old is shrunk more. The opponent-adjusted per-minute stats get the same `m` added to their exposure, which pulls them toward zero, the value of a fighter who did exactly what his opponents usually allow; they have the same tails and no class mean of their own. Style matchups are products of the shrunk rates. With `m = 0` the build is bit-for-bit the M3 build (tested).
- **Alternatives:** clipping at a training quantile (hides the tail without using the reason for it, which is little evidence); a separate prior strength per stat estimated by method of moments (more parameters than one validation set of about a thousand bouts can choose between); shrinking accuracies and shares as well (they have their own denominators and no heavy tails); filling debutants with the class mean.
- **Why not fill debutants:** a fighter with no recorded cage time keeps NaN. The prior is evidence-weighting for a history that exists, not a stand-in for one that does not (D9, D24), and the debut flag keeps its meaning.
- **Costs accepted:** One `m` for stats with very different noise levels. The values shown to a reader for a fighter (`Matchup.a`, `Matchup.b`) are the shrunk ones when shrinkage is on; a page that wants the plain rate must build with `shrink_minutes=0`. The cardio ratios (family 12) are also heavy-tailed but are ratios of two rates, not rates per minute, and are left as they are.

### D34. Swap-invariant level features are candidates, kept apart from the antisymmetric ones
- **Context:** D28 noted that differences drop the level: two 38-year-olds look the same as two 25-year-olds.
- **Decision:** Three columns hold the mean of the two fighters' age, UFC fights and Elo (`lvl_age`, `lvl_n_fights`, `lvl_elo`). Swapping the fighters leaves them exactly equal, because `a + b` and `b + a` are the same floating-point number (tested). They are not in any numbered family and not in the model's default feature list. They go into a model only if validation log loss improves, and the comparison is reported either way in `docs/MODEL_REPORT.md`.
- **Alternatives:** both fighters' raw values as separate columns (the model would then see listing order unless every such pair is handled specially); sums instead of means (same information, harder to read).
- **Why they cannot break symmetry:** the final probability averages the model's output for (A, B) and one minus its output for (B, A). A level feature has the same value in both calls, so it can change how much a difference matters but cannot favour a side. A logistic regression without an intercept gives such a feature a coefficient of zero by symmetry, so the test only concerns the tree models.

### D35. The test period is behind a lock, and the candidate is saved before it is opened
- **Decision:** All rows reach model code through `Splits`, which raises for any bout dated 2025-01-01 or later until `unlock_test` is called. `train` removes test-period rows from the tables before selection starts and never unlocks; every selection stage also asserts the lock is closed. `train` ends by saving the candidate to the registry. `evaluate` is the only command that unlocks, and it scores the candidate it loads back from the registry, after checking the feature file against the hash recorded at training. Each evaluation is appended to `data/models/test_evaluations.jsonl`, and the report prints how many there have been and of which versions.
- **Alternatives:** a convention ("do not look at test"); a single script that tunes and then evaluates in one go; slicing by date wherever rows are needed.
- **Why:** The requirement is that no test-period bout is used before final evaluation and that the test is looked at once per finalized candidate. A convention cannot be tested. With the lock, a test proves that selection gives the same recipe with the test rows deleted, and that each stage refuses to run once the lock is open. Saving first means the thing that is scored is a file on disk with a hash, not whatever was in memory at the end of tuning. The ledger cannot stop someone iterating on the test period, but it makes every look visible.
- **Costs accepted:** The walk-forward backtest also touches the test period (its 2025 and 2026 folds), so it runs inside `evaluate`, under the same unlock.

### D36. P(A) + P(B) = 1 exactly, by construction in floating point
- **Decision:** A model is asked about (A, B) and (B, A), giving `u` and `v`. Inference computes `m = u - v`, the favoured fighter's probability `q = 0.5 + |m| / 2` (which is the average of `u` and `1 - v` for that fighter), calibrates `q` to `c`, and gives the favoured fighter `c` and the other `1 - c`. Probabilities are limited to [1e-6, 1 - 1e-6].
- **Alternatives:** computing `(u + 1 - v) / 2` for A and `(v + 1 - u) / 2` for B; computing A and setting B to one minus it.
- **Why:** The requirement says "exactly", and the test uses exact equality. Averaging each side separately is right only up to rounding, and "B is one minus A" depends on which fighter is called A, so swapping the inputs does not swap the outputs bit for bit. Here `u - v` is exactly minus `v - u`, so `q` and `c` are one number per bout whichever way it is presented, and `c + (1 - c)` is exactly 1 for any double `c` in [0, 1]. The limit at 1e-6 keeps a confidently wrong prediction from having infinite log loss; no model here comes near it.

### D37. Model inputs are the difference features only; details of the logistic baseline
- **Decision:** The candidates read the `d_` features of the thirteen families (plus the level columns if those pass their test). Weight class, bout format and the per-fighter flags stay in the table as context and are not model inputs in this version. Missing values go to the tree models as NaN. The logistic regression has no intercept, divides each feature by its training standard deviation about zero, limits the result to 5 standard deviations, and sets a missing value to 0. Its L2 strength is chosen on validation.
- **Alternatives:** one-hot weight class as an input; median imputation with missing-value indicators for the regression; an intercept.
- **Why:** With difference features and symmetric inference, a context column cannot favour a side; it can only change how much a difference matters, which is what the level-feature test (D34) already probes with three columns chosen for that purpose. Keeping the inputs to the families means the ablation covers every input. For the regression, no intercept makes it exactly odd, so it needs no averaging; a difference feature has mean zero by symmetry, so 0 is both the mean and "no known difference"; an indicator of missingness is the same for both orientations and would get a zero coefficient. The 5-SD limit is a fixed constant so that the baseline is not a straw man on heavy-tailed features.

### D38. Selection in fixed stages, scored over several seeds, with paired intervals
- **Decision:** Order: rate-shrinkage strength, level features, hyperparameter search per library, recency half-life and library, calibration method, ablation. The two feature choices are made with reference settings written down before any result, and judged on validation log loss averaged over XGBoost and LightGBM. A variant's score is its mean over five seeds. Every comparison is reported with a 95% paired bootstrap interval over validation bouts. The search tries 40 settings per library on one seed and re-scores the best five on all seeds.
- **Alternatives:** one joint search over features, settings and half-life; tuning first and choosing features with the tuned settings; choosing by a single run.
- **Why:** Validation has about a thousand bouts, so most differences between options are smaller than their noise. A joint search over hundreds of combinations would mostly select noise. Feature choices come first so that settings tuned on one option cannot tilt the comparison toward it. Seed averaging removes the part of the noise that comes from subsampling; the bootstrap interval shows the part that comes from which bouts happen to be in validation, and the report says so when an interval contains zero rather than presenting a choice as a finding.
- **Costs accepted:** Stages are chosen one at a time, so interactions between them are not explored. The choices are still made on validation, so validation numbers are optimistic; the test period is the measurement.

### D39. One recipe function for the registered model and every backtest fold
- **Decision:** `fit_recipe(recipe, train, valid)` fits on the training rows in both orientations with recency weights, chooses the number of trees by early stopping on validation log loss, and fits the calibrator on validation. The registered model is that function applied once with seed 0. The walk-forward backtest applies the same function to each year's own periods.
- **Alternatives:** a fixed number of trees carried into the backtest; averaging several seeds into one model; refitting on training plus validation after selection.
- **Why:** The number of trees that suits 1,500 training bouts is not the number that suits 6,800, so each fold chooses its own, the same way the registered model did. One seed keeps the saved model a single booster that SHAP can explain in M6. Refitting on training plus validation would produce a model with no validation set left to calibrate on and no measured performance; the registered model is the one that was evaluated.
- **Costs accepted:** The registered model has not seen 2023 onward in training. A production refit on later data is a separate, deliberate step (D4), and the walk-forward backtest is the evidence for how the recipe behaves when refitted.

### D40. Calibration: slope-only Platt or symmetric isotonic, chosen by cross-validation inside validation
- **Decision:** Platt scaling is `sigmoid(a * logit(p))` with no intercept. Isotonic regression is fitted on both orientations of every validation bout. The two are compared by 5-fold cross-validated log loss inside validation, with all bouts of an event date in the same fold; the uncalibrated loss is reported beside them. The chosen method is refitted on all of validation and applied to the favoured fighter's probability (D36).
- **Alternatives:** Platt with an intercept; isotonic on one orientation; a held-out half of validation.
- **Why:** A symmetric model must map 50% to 50%, so the intercept is zero by construction, and an isotonic fit on both orientations is symmetric about 50% for the same reason. Cross-validation uses every validation bout for both fitting and judging, which matters with about a thousand of them. The validation row of the report uses the cross-validated probabilities, because the final calibrator was fitted on those same bouts.

### D41. Walk-forward backtest: refit everything fitted, keep the recipe fixed, and say so
- **Decision:** For each year Y from 2013: fitted feature parameters (Elo, league baseline, class means), the feature table, the model and the logistic baseline use bouts through Y-3; the number of trees and the calibrator use Y-2 and Y-1; Y is scored. That is the registered model's own schedule moved back, so the 2025 fold must reproduce the registered model's probabilities exactly, and `evaluate` checks that it does. The library, settings, half-life, shrinkage strength and calibration method are not re-chosen per fold.
- **Alternatives:** fitting through Y-1 with no calibration; reusing one feature table with parameters fitted through 2022 for every fold; re-running the whole selection per fold.
- **Why:** Reusing the 2022 feature parameters would let a 2015 fold use an Elo K tuned on 2015 outcomes. Re-running selection per fold would cost fourteen searches on validation sets of a few hundred bouts each. The middle course is stated plainly in the report: folds before 2025 were scored with a recipe chosen on 2023 to 2024 and are a backtest, not a held-out result; only the test-period folds are untouched. 2013 is the first year whose training window (through 2010) has at least 1,500 bouts.

### D42. Registry: text model files, content-derived version names, hashes, nothing overwritten
- **Decision:** A version directory holds the booster in its library's own text format, the calibrator and feature list as JSON, the training configuration, the feature settings and fitted parameters the inputs were built with, validation metrics, and a manifest with the git commit, a SHA-256 of the training rows (bout IDs, labels and feature values in order), library versions and a SHA-256 of every file. The version name is the library plus the first characters of the data hash and the configuration hash. Loading verifies every file. Saving the same model again is a no-op; a different model under an existing name is refused. Test metrics are attached once and must match if computed again. Nothing writes `approved.json`.
- **Alternatives:** pickled Python objects; timestamps as version names; hashing the parquet file.
- **Why:** A pickle runs code when loaded and breaks across library versions; text formats load with the library alone and reload to identical predictions (tested). A name derived from data and configuration means the same inputs give the same version, so a rerun is visibly a rerun. The row hash does not depend on parquet encoding, so it changes only when what the model saw changes. Storing the feature settings and fitted parameters beside the model is what lets M5 build prediction inputs that match training.

### D43. Metric conventions
- **Calibration error** is measured on the favoured fighter: ten equal-width bins of max(p, 1 - p) from 50% to 100%, the gap between mean probability and the favourite's win rate, weighted by bin size. It does not depend on which fighter is called A.
- **Accuracy** counts a bout as half right when a model gives exactly 50% (two debutants with equal ratings under Elo). "Pick the higher-rated fighter" is the accuracy of the Elo probability, since both pick the same fighter.
- **Draws and no contests** are counted per period as "no result" and are not scored.
- **By weight class** is reported only for classes with at least 100 scored bouts in the period.

### D44. Bouts with an attribute gap are not fitted on (a leak found during M4)
- **Context:** The first selection run was checked before the test period was opened. On the training period, in bouts where one fighter's profile lacks a physical attribute (height, reach, stance or date of birth) that the other's has, the fighter with the complete profile won the large majority; the count and the share, by period, are in `docs/MODEL_REPORT.md`. The reason is in the source: profiles are as they stand today (leakage rule 3, D22), and in older years a missing reach or date of birth mostly belongs to a fighter who had a bout or two and left. So which fighter has the gap is information from after the bout. The difference feature is NaN whichever fighter is missing the value, but a model can work out which one from the rest of the row (a debutant against a veteran, for example).
- **Decision:** The feature table carries two per-fighter flags, `a_attr_gap` and `b_attr_gap`. A bout where either is set is left out of every fit: the candidates, the logistic baseline, and each walk-forward fold. Bouts where both profiles are equally incomplete stay in, because nothing in them distinguishes the fighters. Bouts with a gap are still predicted and scored, in validation, test and the backtest, and the report shows them as their own group.
- **Alternatives:** filling the missing difference with zero (a tree can still isolate an exact zero in age, so the signal survives); dropping height, reach, stance and age from the model (the physical family is the strongest in the ablation); keeping the bouts and reporting the effect.
- **Why:** The rule is that no feature may use anything after the bout, and this one did, through absence rather than value. Leaving the bouts out is the one treatment that makes it impossible, not just harder, for a model to associate a gap with an outcome: it never sees the two together. It matters in practice. Validation has no such bouts, so validation scores could not show the problem, while the test period and live cards have many, for a different reason: recent debutants whose profiles were captured before they were filled in (`docs/DATA_QUALITY.md`). A model that had learned "the fighter with the gap loses" would have applied it to them.
- **Costs accepted:** A share of training bouts is not fitted on, most of them from the older years (the count is in the report). A model now sees a missing height, reach or age difference only in bouts where both fighters lack it, so how it treats a one-sided gap at prediction time is whatever the trees do with a missing value there; it cannot favour a side beyond what the other features say, and the report measures how well it does on those bouts. The same survivorship could in principle show through other profile fields if any are added later; the rule applies to them too.

### D45. Diagnostics may read the test period, under their own name and their own ledger
- **Context:** The test period scored better than every backtest year (`docs/MODEL_REPORT.md`). Finding out whether that is a leak means looking at test-period bouts in ways `evaluate` does not: by profile capture time, with inputs removed, with old models.
- **Decision:** `uv run python -m ufc.models.diagnostics` is a second command that opens the lock (D35). It unlocks under a name that says what it is ("era-shift diagnostic of <version> (analysis only)"), appends every run to `data/models/test_diagnostics.jsonl`, and writes only under `data/reports/diagnostics/`. It saves no model, writes nothing to the registry, and its results are not an input to selection: the candidate, the recipe and every choice in the selection record stay as they were. Its unmodified run must repeat the saved backtest exactly, and it records whether it did.
- **Alternatives:** adding the breakdowns to `evaluate` (every diagnostic would then count as a test evaluation of the candidate and rewrite its recorded metrics); doing the analysis in a notebook (no record that the test period was looked at); not looking (leaving a possible leak unexamined in a project whose point is credibility).
- **Why:** A leak check is not model selection, but it is still a look at the test period, and the ledger exists so that every look is visible (D35). A separate ledger keeps the count of evaluations in the report meaning what it says, one scoring of one candidate, while leaving a trace of the analysis.
- **Costs accepted:** The test period is no longer untouched in the strict sense: its bouts have now been described by year, by debut date and by feature. Any change to the model made after reading the diagnostic would be a choice informed by test data and would have to be reported that way; the first live results are the clean measurement.

### D46. Correction to D14 and D22: upstream has refreshed profiles once; nothing is changed yet
- **Finding:** D14 and D22 say upstream captures height, reach, stance and date of birth once and never refreshes them. Its history says otherwise (`scripts/profile_history.py`; numbers in `docs/MODEL_REPORT.md`, "Era-shift diagnostic", check 6): no existing profile changed between the commits of 2024-12-11 and 2025-09-30, a large share changed between 2025-09-30 and 2025-11-14 (mostly empty attributes filled in, some values corrected), and none has changed since. New fighters are still captured when first listed, usually empty.
- **Decision:** Record it and change nothing in this session: the investigation was analysis only. The feature pipeline, the candidate and the selection record are as they were.
- **Why it matters:** (1) Leakage rule 3's "static" assumption was defended in D22 as "static as of first capture". It is static as of the last refresh, which for most 2025 bouts is after the bout. The diagnostic finds no sign that this helps the model pick winners. (2) Bouts fought before the refresh were scored with attributes a live run would not have had. Measured on January to September 2025 with the profiles upstream held then, the saved model's log loss is about the same (the figures are in check 6), so the test result does not depend on it; bouts after the refresh are scored as a live run would score them. (3) Missing attributes for new fighters will persist until upstream refreshes again, on a schedule this project does not know.
- **Open:** whether to build test-period and backtest features from the upstream commit current on each bout's date (an honest "as available" table), and whether M5 should take new fighters' attributes from somewhere else. Both are the user's call.

### D47. Production refit: the candidate's recipe on every bout, calibrated out of time
- **Decision:** `uv run python -m ufc.models refit` fits the recipe of the tested candidate on every completed bout and saves it as a new registry version. Its manifest has a `lineage` entry naming the candidate and the status "production refit; no held-out test; recipe validated by the candidate". Nothing about the recipe changes: library and settings, half-life, shrinkage strength, feature list (level features included) and Platt calibration are read from the candidate. Every fitted step is refitted through the latest event: Elo parameters, league baseline, weight-class means, and the booster (on bouts with a winner and no attribute gap, D44). XGBoost has no scalers. The Platt slope comes from a second model fitted with the same recipe on bouts through 2024-12-31, with its feature parameters also fitted through 2024. Its predictions for bouts from 2025-01-01 on are out of time, and the slope is fitted on them, leaving out attribute-gap bouts as every other fit does. The final booster then gets that slope. Both boosters have the number of trees the candidate's own schedule chooses (fitted through 2022, early stopping on 2023 and 2024): 405. `evaluate` refuses a refit, and a refit cannot be refitted.
- **Alternatives:** keep the candidate as the live model (fitted through 2022, so it would never see the four most recent years); refit and calibrate on the bouts the booster was fitted on (in-sample probabilities are too confident, so the slope would be wrong in a known direction); keep 2025 onward out of the booster to calibrate on (the live model would miss its most recent two years); choose the final booster's trees by early stopping on the last two years of its own window.
- **Why:** For predicting next week's card, the most recent bouts matter most, and the recipe, not one fitted booster, is what validation and the test period measured. Calibration needs predictions the model did not fit, so the slope comes from a model that stops at 2024, and its feature parameters stop there too, or Elo tuned on 2025 outcomes would make those predictions less out-of-time than they look. The tree count follows from that: the slope was fitted for a booster of 405 trees. Early stopping inside the final window chose 786, and that booster's logits were 16% larger than the calibration model's on the bouts both were fitted on. A slope of 1.39 applied on top would have stacked two kinds of sharpening. With 405 trees the difference is about 4%. The numbers are in `docs/MODEL_REPORT.md`, "Production refit".
- **Costs accepted:** (1) The calibrator was fitted for a different booster. The final booster has seen about 900 more bouts, and its features use Elo parameters fitted through the latest event, so its logits are about 4% larger in mean absolute value than the calibration model's on the same bouts. Applied unchanged, the slope makes the refit somewhat more confident than the out-of-time evidence supports, if that difference carries over to new bouts. It cannot be measured, because nothing is held out. (2) The slope (1.39, against the candidate's 1.22) was fitted on 2025 to 2026, when the model scored better than in any earlier year for reasons the era-shift diagnostic did not establish. If those conditions do not persist, the refit will be overconfident. (3) The refit has no held-out test. From now on its only out-of-sample evidence is live predictions published before events. (4) Keeping the candidate's tree count rather than early stopping is a choice about the size of the booster, made to keep the calibration valid; a larger window might support more trees, and nothing here can show it.

### D48. Upcoming cards: the MediaWiki API, tables of their own, keys from page IDs
- **Decision:** `src/ufc/predict/` reads "List of UFC events" and each scheduled event page through the MediaWiki API only (`query` with `prop=revisions`, up to 50 titles per request). The client sends a User-Agent naming the project with the public repository URL as contact (overridable with `UFC_WIKI_CONTACT`), makes one request at a time at least a second apart, sets `maxlag`, retries 429, 5xx and maxlag answers with backoff, and caches responses on disk (cards one hour, fighter articles a week). A refresh makes two to four requests. Upcoming events, bouts, provisional fighters, backfilled attributes, predictions and a refresh log live in new tables; nothing writes the ingest's tables. An event's key is `wp:<page ID>`, and a bout's ID is `wb` plus 16 hex characters of a SHA-256 over the event's page ID and the two fighters' normalised names, sorted.
- **Alternatives:** `action=parse` per page (one request per event); scraping rendered HTML; putting upcoming bouts in `events` and `bouts` with invented 16-character IDs; keying events by page title; keying bouts by resolved fighter IDs.
- **Why:** Batched `query` requests and a cache are what Wikimedia's etiquette asks for, and wikitext templates are stabler than HTML. Separate tables mean an upcoming bout can never be mistaken for a completed one by the feature pipeline, the ingest load can never touch them, and an upstream value can never be overwritten. Event pages are renamed whenever a headliner changes; the page ID survives a rename, the title does not. Names rather than resolved IDs go into the bout ID so that a provisional fighter later linked to a UFCStats profile keeps the same bout, and sorting makes the ID independent of which corner Wikipedia lists first.

### D49. Card fighters resolve with the ingest's rules; unknown names are provisional, with a guard
- **Decision:** A card fighter's displayed name, and the linked article title without its disambiguation suffix, go through the ingest's resolver (overrides, a name of exactly one profile, a shared name settled by weight class), built from the same snapshot files with the same code (`build_profiles`). `src/ufc/predict/wikipedia_overrides.csv` adds overrides for names as Wikipedia writes them, each with its evidence. A name that matches no profile makes a provisional fighter keyed by article title (or by name, without an article), predicted as a debutant and linked to the UFCStats ID once the name resolves. A shared name the weight class does not settle, two names pointing at different profiles, a placeholder ("TBD") or both corners resolving to one fighter make the bout unresolved: stored, reported, not predicted. One guard: if a provisional fighter's article cites a UFCStats profile URL whose ID is in the dataset, he is not a debutant, and the bout is unresolved with that ID in the reason until an override is added.
- **Context:** The first live run made five veterans provisional, because Wikipedia writes "Sharabutdin" for "Shara", "Park Jun-yong" for "JunYong Park", and so on. Predicted as debutants, they would have been silently wrong. Two of the five articles cite the fighter's UFCStats profile; the other three were checked by hand (date of birth, weight class, the only profile with that surname). All five are now overrides.
- **Alternatives:** fuzzy matching (rejected in D17 for the reason it was rejected there); matching on the cited UFCStats ID automatically (an editor's citation is evidence, not an identifier this project controls); treating every unknown name as unresolved (most cards have real debutants, and D9 says they are predicted).
- **Why:** One set of rules means a name means the same fighter in training data and in predictions. A wrong match corrupts every feature silently; an unresolved bout is visible in the refresh summary and fixed with one line of evidence. The guard turns the most common failure, a veteran under a different spelling, from a silent error into a reported one, without making the citation itself a matching rule.
- **Costs accepted:** A veteran whose name differs and whose article cites no UFCStats profile (or who has no article) is still predicted as a debutant until someone adds an override. The refresh summary lists provisional fighters so that a person reviews them before trusting a card.

### D50. A card is applied whole or not at all; failures change nothing
- **Decision:** If "List of UFC events", the batch of event pages, or the provisional fighters' articles cannot be fetched, the refresh stops before any card is applied. For each event, a missing page or a parse error leaves its stored bouts exactly as they were. A parsed card is also refused when it has no bouts where some were stored, or when, with at least four bouts stored, more than half would disappear at once. Otherwise the card is applied in one transaction: new pairings are inserted, listed ones get a new `last_seen_at`, a pairing no longer listed is marked `cancelled` with its current prediction superseded, and a cancelled pairing that returns is restored. A replacement opponent is a new pairing, so the old bout is cancelled and the new one predicted. A scheduled event that drops out of the list becomes `unlisted` and is no longer published, but its bouts are not cancelled. Every failure goes to `refresh_log` and the summary.
- **Alternatives:** applying whatever parsed (a vandalised or half-edited page would cancel a card); cancelling bouts of events that leave the list; per-bout thresholds.
- **Why:** Wikipedia is untrusted input (D16). Real cards lose one or two bouts at a time; losing most of a card in one edit is far more often a broken page than a real change, and wrongly cancelling a bout supersedes a live prediction, which cannot be undone. Refusing a suspicious card costs one refresh cycle; the next run applies it if the page is right.
- **Costs accepted:** A real mass change (an event cancelled and its page emptied) is held back and logged until a person looks at it. The thresholds are judgment, not measurement.

### D51. Missing height, reach and date of birth from fighters' Wikipedia infoboxes, for predictions only
- **Decision:** For fighters on upcoming cards, any of height, reach and date of birth that the dataset lacks is read from the infobox of the article the card links to, in a few unambiguous formats and within plausible ranges, and stored in `attribute_backfill` with its source, article and revision. The `fighters` table is never written. When attributes are merged for prediction an upstream value always wins, including one that appears after a value was backfilled. Each prediction records the source of every attribute of both fighters. Stance is not backfilled: infoboxes do not state it reliably.
- **Alternatives:** leave the gaps (D46 shows recent debutants mostly lack height and reach, so many bouts would be attribute-gap bouts, where the model scored 0.7251 on the test period); write the values into `fighters`; backfill training data too.
- **Why:** The missing values are a capture-time artefact of the source, not missing facts. Filling them at prediction time moves upcoming bouts toward the kind of bout the model was fitted on (D44). Keeping the values in their own table with a source makes "never overwrite upstream" true by construction and keeps training data exactly what was evaluated.
- **Costs accepted:** Training and prediction now read attributes from two sources for some fighters. Wikipedia's values can be wrong; the plausibility ranges catch gross errors only.

### D52. Staleness: completed events the dataset does not have yet
- **Decision:** Each refresh compares the dataset's latest event with completed events on Wikipedia (the past-events table, and scheduled-table events dated before today). Events after the dataset's latest are "missing": the global status is `current` with none, `behind` with some, and `unknown` if a missing event's page cannot be read. A bout is labelled "stale stats" when either fighter (by resolved ID or by normalised name) fought on a missing event; with status `unknown`, every bout is, because it cannot be ruled out.
- **Alternatives:** comparing only dates (says the dataset is behind, not which bouts it affects); refusing to predict when behind.
- **Why:** The dataset lags the sport by a day or more and could stop. A fighter whose last fight is missing is predicted without it, which matters most for exactly the bouts people watch (quick turnarounds). Labelling is honest without blanking the card.

### D53. Predictions: immutable rows, replaced only when their inputs change
- **Decision:** Every resolved, scheduled bout of an event dated after today (UTC) is predicted with the model `approved.json` names, from `build_matchup` at the event date, using the feature settings and fitted parameters stored beside the model. A prediction row is never edited except to set `superseded_at` and a reason. A bout gets a new row when the SHA-256 of its inputs changes (model version, both fighters, event date, weight class, every model input, and the limited-data reasons); otherwise the current row stands. A bout is labelled "limited data", with reasons, for a debut, an attribute gap after backfill, or stale stats. `is_live` is 1 for a prediction made before the event date. The JSON dump in `data/publish/` is written only when the validation gate in ARCHITECTURE passes, and the last good file stays otherwise. No approved model means no predictions and no publish.
- **Alternatives:** a new row on every refresh (thousands of identical rows, and the "first prediction" of a bout would mean nothing); updating rows in place (destroys the live record); predicting events dated today.
- **Why:** The live track record is the only out-of-sample evidence for the refit (D47), so each published number must be preserved exactly as it was shown. Hashing the inputs ties a new row to a real change. An event dated today may already be under way, and a prediction made then is not "before the event".


### D54. M4.5 model revision: question, variants and adoption rule, registered before any variant was run
- **Context:** A review of upcoming predictions found age to be the largest SHAP contribution in bouts where an older, higher-rated fighter meets a much younger one. Hypothesis: age-gap bouts are confounded with matchmaking (declining veterans booked against prospects), so the model over-penalises age when the older fighter is still elite. The question came from looking at upcoming bouts; no upcoming bout is used in any measurement or decision below.
- **Step 1, done before this entry was written** (`uv run python -m ufc.models.revision run --variants base`): the slice is bouts where one fighter is at least 6 years older and rated at least 50 (or 100) Elo points higher; the mirror slice has the older fighter rated lower by as much. The unchanged recipe does not underrate the older fighter in the slice on any period scored so far; the numbers are in `docs/MODEL_REPORT.md`, "Model revision M4.5". The rule below therefore asks for calibration to improve in either direction, not for predictions to move toward the veteran.
- **Variants**, each added to the candidate's recipe with nothing else changed (library, settings, half-life, shrinkage, level features, calibration method; no re-tuning): (a) `schedule`, a new family 14: best win and worst loss by the opponent's Elo at the time, and wins and losses against opponents then rated above the fighter; (b) `age_shape`: years past 32 and years past the weight class's median age (fitted on training) as differences, and the bout's mean age relative to the class median as a swap-invariant level column; (c) `catch_weight`: a catch-weight bout counts as the division of the fighter's adjacent bouts in "fights at this weight" and the weight-change features; (a+b+c) `combined`. (d), the calibration window of the production refit, cannot be scored on validation and is reported, not adopted or rejected.
- **Adoption rule.** A variant is recommended for adoption only if all three hold:
  1. *Validation log loss is not worse beyond noise:* uncalibrated validation log loss, mean over seeds 0 to 4 (the selection convention, D38); the 95% paired bootstrap interval of variant minus base must not lie entirely above zero.
  2. *The elite-veteran slice is better calibrated on the backtest:* older by at least 6 years and rated at least 50 points higher, walk-forward folds 2013 to 2024 (seed 0, the registered schedule): the absolute gap between mean predicted and actual win rate of the older fighter is smaller than the base's, and the slice's log loss is lower.
  3. *The same slice on validation does not get worse:* seed-averaged, cross-validated Platt probabilities on 2023 to 2024; slice log loss not higher than the base's.
  The +100 slice and the mirror slices are reported, not part of the rule. If several variants pass, the recommendation is the one with the lowest validation log loss, and a difference inside the interval goes to the variant that adds fewer inputs.
- **What is not evidence:** the 2025 and 2026 folds read the test period, which has been looked at before (D45). They are reported as a secondary, already-seen check and logged in `test_diagnostics.jsonl`; they cannot make a variant pass or fail.
- **Why written down first:** the elite slice holds about 350 backtest bouts and about 50 validation bouts, so its numbers are noisy, and four variants with several slices each give plenty of ways to find an improvement by chance. Fixing the slice, the threshold, the periods and the direction-neutral criterion before any variant result exists is what lets a reader trust a "pass".

### D55. M4.5 candidate features: built beside the model features, never inside them unless adopted
- **Decision:** The candidates of D54 are computed by the feature pipeline and written to the feature table and to `Matchup.candidates`, but they are not in `FEATURES` (the thirteen families) or `LEVEL_NAMES`. A model reads them only if its feature list names them; `train` does not add them, and every saved model predicts exactly as before (checked on all current predictions and, column by column, on the full feature table). Catch-weight resolution is a setting, `FeatureConfig.catch_weight_adjacent`, off by default; a saved pipeline without the setting reads as off.
- **Strength of schedule (`schedule`, proposed family 14):** for each earlier bout the store keeps both fighters' ratings from before that date, the same as-of ratings the Elo feature uses. Best win is the highest such rating of an opponent the fighter beat, worst loss the lowest of one he lost to (NaN with no win or no loss; a draw or no contest counts in neither); two counts give wins and losses against opponents then rated above him. Four difference features.
- **Age shape (`age_shape`):** years past 32 and years past the weight class's median age, each `max(0, age - threshold)`, as differences; and `lvl_age_rel_class`, the bout's mean age minus the class median, as a swap-invariant level column. The medians are fitted on training bouts only (each fighter in each bout with a known date of birth counts once); a class needs 50 training bouts and a fixed weight limit, otherwise the median over all training bouts is used. They are stored with the other fitted parameters. **Changed from the request:** "age relative to the class median, as a difference" would be exactly `d_age`, because both fighters in a bout share its class and the median cancels; the hinge at the class median and the level column are the forms that carry new information.
- **Catch weight:** for "fights at this weight" and the move up / move down features, a catch-weight bout in a fighter's history counts as the division of his nearest earlier bout with a known division, or failing that the nearest later one that is still before the cutoff; a catch-weight bout being predicted counts as his most recent known division. With no such neighbour it stays a catch weight. Only bouts before the cutoff are ever consulted, so a past bout's resolved class can change as the cutoff moves forward; that is as-of, not a leak, and the perturbation and same-card tests run with the setting on.
- **Alternatives:** adding the candidates to `FEATURES` directly (every future `train` would then include them whether or not they were adopted, and the families of the M4 ablation would silently change); a separate experimental feature builder (two code paths for features is what D23 rules out).
- **Costs accepted:** every build computes seven columns that no live model uses, and the feature table has columns outside the numbered families until the user decides on adoption.

### D56. M4.5 outcome: the elite-veteran hypothesis is not supported; `age_shape` passes the rule, weakly
- **Finding:** on validation and on the 2013 to 2024 backtest the unchanged model does not underrate an older, higher-rated fighter against a much younger one; it overrates him slightly, and it overrates older fighters across every 6-year age gap. The large SHAP contribution of age in such bouts is the model correcting Elo, which overrates them far more. Numbers: `docs/MODEL_REPORT.md`, "Model revision M4.5".
- **Rule outcome (D54):** `age_shape` and `combined` pass; `schedule` and `catch_weight` fail. `combined` is not distinguishable from `age_shape` on validation, so the tie-break selects `age_shape` (three inputs).
- **Recommendation:** the candidate's recipe plus the three `age_shape` inputs, with nothing re-tuned. Not applied: no candidate saved, no refit, `approved.json` untouched. Adopting it means moving the three columns into the model's feature list (a family of their own, so the ablation keeps reporting them), saving a candidate with the fixed recipe, and refitting it; an `evaluate` of that candidate would score a test period that has already been looked at (D45) and should be reported as such.
- **Why recommend a weak pass:** the rule was fixed before the variants were run so that the decision would not be made by looking at the results. Overriding it now because the margin is small would be the same mistake in the other direction. The report states how weak the pass is: validation log loss is 0.0011 higher (inside the noise), the slice improvements are inside their intervals, and the only clear gain is on the backtest overall. Keeping the current recipe is a defensible alternative and is the user's call.
- **What stays:** the `schedule` and `catch_weight` code stays as candidates outside the model's features (D55), so the comparison can be rerun on later data with one command.

### D58. M4.5 adopted: `age_shape` becomes family 15; the next refit uses the rolling calibration window
- **Decision:** The user adopted the M4.5 outcome. The two age-shape differences join the model's features as family 15 ("age shape"; 14 stays the unadopted `schedule` candidate), placed after every M4 column, and `lvl_age_rel_class` becomes a swap-invariant column *owned by* that family: it enters and leaves the model with the family, and the ablation removes all three together, not with the optional level group. The new candidate `xgboost-ed7a4d35-852c380d` was saved by `train --recipe-of xgboost-71fab189-44ddd3f0`: the M4 recipe with the current families and nothing re-tuned (trees by early stopping and the calibrator on validation, ablation rerun, selection stages 1 to 3 carried over from the parent's record and marked as carried). Records go to `data/reports/m45/`, so the M4 records in `data/reports/eval/` and the generated block of `docs/MODEL_REPORT.md` still describe the M4 candidate. Numbers: `docs/MODEL_REPORT.md`, "Production model after M4.5".
- **Why a fixed recipe and not a fresh `train`:** the rule in D54 judged the M4 recipe plus three columns. Re-running the whole selection could change shrinkage, hyperparameters or half-life, and the saved model would be a recipe nobody had measured. The fixed path reproduces the M4.5 variant's validation score to every recorded digit, which shows the saved candidate is the one that passed. The cost is that stages 1 to 3 were chosen without family 15; the record says so instead of hiding it.

The level column describes the bout's age relative to its division, so it means nothing without the age-shape differences. Putting it in the optional level group would let the level test drop it on its own.

One-family-at-a-time ablation reports such overlaps poorly, and the report says so. The candidate has 307 trees against 405, because early stopping chose it. Approval stays manual: `approved.json` names `xgboost-ffc3ca8c-ee729619` until the user changes it.

### D59. A plain-language "why" per bout, built by templates from SHAP factors
- **Decision:** Every new prediction stores, in `shap_json`, the symmetrised TreeSHAP contribution of each input toward fighter A, `(phi(A, B) - phi(B, A)) / 2`, and a `why` built from them by `src/ufc/predict/explain.py`. The `why` names the favoured fighter (higher calibrated probability), the three reasons the model weighs most toward them and the one it weighs most toward the other fighter. Each reason is a fixed template filled with both fighters' as-of values ("12.4 years younger (27.6 vs 40.0)", "a 157-point rating edge (1,642 vs 1,485)"). Inputs that measure the same thing are summed into one reason: age with UFC fight count, cage time, debut and the age-shape columns; Elo with opponent quality; each per-minute or percentage stat with its opponent-adjusted version across all windows. Everything else is grouped by stat or family. `predictions.json` carries the `why` for each bout.
- **Alternatives:** an LLM writing the text (not reproducible, can state things the model never weighed, and the analyst is a separate, later feature); one reason per raw input (the top three would often be the same stat in three windows); grouping by family (too coarse: "striking" would merge strikes landed with strikes absorbed); SHAP from the `shap` package (another compiled dependency; XGBoost and LightGBM compute TreeSHAP themselves).
- **Why:** symmetrising makes the explanation obey the same rule as the prediction. Swapping the fighters negates every contribution exactly, so the swapped bout gets the same sentence about the same people, and a test checks this word for word. Summing correlated inputs avoids a misleading picture: SHAP splits credit among correlated inputs, so "age" alone can look small or large depending on how much of it went to fight count. The wording says what the model *weighs*, never what causes a result, because SHAP measures the model, not the sport. A test rejects causal phrasing.
- **Costs accepted:** contributions are on the booster's log-odds before calibration. They rank reasons correctly, but they do not add up to the published probability. With a calibration slope at or below zero the calibrated favourite could have no reason pointing its way; the text then says so instead of inventing one. The reason's displayed value is the member input with the largest weight, so a reason built from six windows shows one of them. Rows made before this change have no `why` and publish `null`; predictions are immutable (D53), so they get one when their inputs next change, for example when a new model is approved.

### D60. Read-only `show` and `matchup` commands
- **Decision:** `python -m ufc.predict show [--event NAME | --all]` prints stored predictions; `matchup "A" "B" [--date] [--weight-class]` predicts a hypothetical bout with the approved model. Both open the database with SQLite `mode=ro` (so not even the schema step of `connect()` can run), never insert into `predictions`, and never touch `data/publish/`. `show` reuses `publish.snapshot` for the rows. `matchup` resolves names with the card rules (`resolve_fighter`); an ambiguous name is an error naming the cause, and a name with no profile is "not found", not a provisional debutant, because a made-up fighter has no history to predict from. The output is headed "HYPOTHETICAL, NOT STORED".
- **Default division:** the class both fighters have fought at, choosing the smallest sum of each fighter's recency rank (most recent class = 0), the first fighter's order breaking ties; only bouts before the date count. No shared class is an error asking for `--weight-class`.
- **Alternatives:** taking the first fighter's latest class (can pick a division the other has never fought); fuzzy name matching (rejected by D17); letting `matchup` store its result flagged hypothetical (puts non-bouts in the track record's table).
- **Costs accepted:** a hypothetical makes no stale-stats check (that needs the Wikipedia event list, which these commands never request) and says so. A past `--date` is allowed and uses only bouts before it, but Elo-based inputs there have not been audited for that use; treat such output as exploratory.

### D61. Odds sources for M12: The Odds API for history and forward capture; no scraping of BestFightOdds
- **Decision:** `docs/ODDS_SOURCES.md` records the research. Recommended: (a) for the historical backtest, The Odds API historical endpoint for one paid month (mid-2020 onward, timestamped snapshots, named books), with UFCalendar's free consensus close as a cross-check; (b) for forward capture, The Odds API free plan, one `h2h` call per snapshot (1 credit), raw responses stored untouched with request time, started before the next card. Nothing was bought, registered or downloaded, and no code was written. Spending and sign-up are the user's call.
- **Alternatives:** scraping BestFightOdds (robots.txt allows crawling and its terms are silent, but silence is not a licence, it can show a bot challenge, and it has no timestamps or bulk route); the `ufcscraper` package (Selenium against BFO with no robots check, no delays and a loop that waits out a human-verification page, plus it requires UFCStats, which D13 and rule 5 forbid); free datasets (Kaggle's end in 2020, the GitHub one is unlicensed and from betmma.tips, the Hugging Face one has a "single-commercial-user" licence and under 1K rows); UFCalendar alone (clear terms, but a 100-requests-a-month free tier, no bulk export and a vendor-defined consensus close).
- **Why:** the project's rules are the same for odds as for stats: no defeating bot protection, terms recorded plainly. The Odds API's terms explicitly allow storing, deriving values and training models, and forbid only standalone redistribution, which we do not do. Real snapshot times let the backtest say what price existed before the bout. Its history starts mid-2020, which covers validation, test and every walk-forward fold after 2020.
- **Costs accepted:** no odds before mid-2020; the historical cost per call, snapshot spacing and which books carry MMA are from page summaries or unverified and need one live call; vendor-labelled "closing" is a snapshot, not a sportsbook's published close; public pages may show derived values only, never raw vendor odds. "Closing" must be defined in `ML_REQUIREMENTS.md` before any results are seen.

### D62. Forward odds capture, and the betting evaluation fixed before any odds results
- **Decision:** `uv run python -m ufc.odds snapshot` (`src/ufc/odds/`) makes one call to The Odds API's MMA `h2h` market (default regions `us,eu`, 2 credits), stores the raw bytes unchanged in `data/odds/raw/<UTC timestamp>.json` with a `.meta.json` sidecar (request time, credit headers, SHA-256), and prints a summary. It reads the quota from the free `/sports` endpoint first and refuses below 50 credits. The key comes from `.env`, travels in the documented `x-api-key` header so it is never in a URL, and every error text is redacted. It writes no database rows and matches no bouts; that is M12. The betting evaluation is in `docs/ML_REQUIREMENTS.md` ("Betting evaluation"): Pinnacle `h2h` as the reference price; closing is the last snapshot at or before the card start (the earliest bout `commence_time`), at most 24 hours old; proportional vig removal; and three flat $100 strategies (market favourite, model pick, model edge of at least 5 percentage points). **These definitions were fixed on 2026-11-18, before any odds results were seen:** the only odds data at that point is one live snapshot, which was inspected for bookmaker coverage and start times, not for prices against model picks, and no historical odds exist in the repo.
- **What the live call settled (`docs/ODDS_SOURCES.md` section 2a):** Pinnacle carries the UFC bouts and is in the `eu` region; `commence_time` is per bout and covers all MMA promotions; the call cost 2 credits for 2 regions; historical odds cost 10 credits per market per region and need a paid plan.
- **Alternatives:** a US-only call (1 credit, but no Pinnacle, the sharpest and tightest-vig book); consensus across books as the reference (smoother, but includes soft and stale books and mixes whose price is used); closing as one fixed time before the card (ignores that later bouts start hours after the first); choosing the edge threshold after seeing a sweep (the classic way to find a profitable-looking rule that is noise); the key as an `apiKey` query parameter (the documented default, but it ends up in every URL an exception or proxy log can print).
- **Costs accepted:** requiring Pinnacle excludes bouts it does not price (counted and reported); card start as the earliest bout is conservative for later bouts, whose lines may move after it; the free plan's own rate limit is unknown, though one call per capture makes that moot; the default two regions doubles the credit cost, still about 12% of the free quota for five cards a month at six calls each; a model-pick or edge strategy tested on 2025 onward uses test-period predictions, which the stats evaluation had already opened (D58), so the sample is not new data, and live bouts are the only fully out-of-sample check.

### D63. M4.6 "expected outcome" features: data check, design and adoption rule, registered before any variant was run
- **Question:** results are a noisy measure of performance (a lucky knockout, a close or bad decision, a draw from a point deduction, credit for facing strong opponents while losing every exchange). Do as-of features built on how a fighter *performed*, rather than on what the result said, improve the production recipe?
- **What the data supports (checked before this entry; counts only, no model run):** judges' scorecards are in the dataset, as each judge's bout total in the results file's details text (for example `Judge 29 - 28.`), for 4,113 of 4,169 decisions, every one from 2001 on and none before; there are no per-round cards. For decision wins the totals are written loser first, so they give the margin but not a per-fighter orientation; for draws the orientation cannot be recovered. Point deductions are written into the same text (`Point Deducted: <foul> by <surname>`) in 34 bouts, all decisions. Per-round stats (strikes, knockdowns, takedowns, submission attempts, reversals, control) exist for every bout with stats; control time is missing before 2000 and for part of 1999.
- **Performance model (a fitted transform, leakage rule 4):** a logistic regression without intercept on A-minus-B in-fight differences, so P(A) and P(B) are mirror images. Fitted on bouts through the training cut-off (2022-12-31 for validation, Y-3 in walk-forward fold Y) that ended in a decision with a winner and have stats; label = the judged winner; both orientations; inputs divided by their training standard deviation; L2 with C = 1, not tuned. Inputs: significant strikes landed, knockdowns, takedowns landed, submission attempts and control minutes, each per 5 minutes with the fight counted as at least 5 minutes (so a 30-second finish is not read as an extreme rate); and per-round dominance, (rounds A led minus rounds B led) / rounds fought, on significant strikes landed and on control time. A bout with control missing in any round uses a second fit without the two control inputs. A bout without stats has no deserved value (NaN, never 0.5).
- **Deserved win probability:** the model applied to every bout with stats, decisions, finishes (stats up to the stoppage) and draws alike, from each fighter's own side. For a finish it means "who was winning on the judges' criteria when it ended", which is the point: a knockout by a fighter who was losing scores low.
- **Family 16, `performance` (a candidate, outside `FEATURES` until adopted, like D55), seven A-minus-B differences of as-of values over bouts strictly before the date:** deserved share, career, last 3 bouts and time-decayed (the pipeline's 730-day half-life); luck = actual (1 win, 0 loss, 0.5 draw; no contests left out) minus deserved, career and last 3; a performance Elo, the D26 tracker updated with the deserved share as the score instead of the result, finish multiplier 1, K and provisional multiplier chosen on the training period by log loss of its pre-fight probabilities against the actual winners (grid K 16 to 256, provisional 1 to 2.5), rating only bouts that have a deserved value and a result Elo rates; and deserved share against strong opponents, weighted by max(0, the opponent's standard Elo before that bout - 1500), NaN when no earlier opponent was above 1500.
- **Comparison:** `base` is the recipe of `xgboost-ed7a4d35-852c380d` (M4 recipe plus family 15), the recipe of the approved refit; `performance` adds the seven columns and changes nothing else (no re-tuning). Validation: 2023 to 2024, pipeline fitted through 2022, seeds 0 to 4. Backtest: walk-forward folds 2013 to 2024, the registered schedule, seed 0.
- **Adoption rule.** Family 16 is recommended for adoption only if both hold:
  1. *Validation:* the paired difference in per-bout validation log loss, `performance` minus `base`, uncalibrated and averaged over seeds 0 to 4 (the selection convention, D38), is negative, and the upper end of its 95% percentile bootstrap interval (2,000 resamples of validation bouts, seed 0) is below +0.001.
  2. *Backtest:* pooled log loss over the 2013 to 2024 folds is lower for `performance` than for `base`.
- **Reported, not part of the rule:** calibrated validation log loss, per-seed differences, per-year backtest differences, the per-family ablation rerun with family 16 in the model (seeds 0 to 4), the performance model's accuracy on 2023 to 2024 decisions and its agreement with scorecard margins, and the 2025 to 2026 folds. The last read the test period, which has been looked at before (D45, D58): they are a secondary, already-seen check, logged in `test_diagnostics.jsonl`, and cannot make the family pass or fail. Example bouts, including test-period ones, are descriptions of the transform and are not used for any decision.
- **Why written down first:** the inputs of the performance model, the seven columns and the rule are fixed before any of them has been scored, so a "pass" cannot come from trying variants until one wins. A defect found while building (a bug, not a disappointing number) may be fixed before the run and will be recorded.

### D64. M4.6 outcome: family 16 fails the pre-registered rule; not adopted
- **Finding:** with the seven family 16 columns added to the M4.5 recipe, uncalibrated validation log loss is 0.0002 higher (95% interval -0.0033 to +0.0035; per seed the sign flips) and the 2013 to 2024 backtest is 0.0005 higher. Both D63 criteria fail. The ablation rerun with family 16 in the model gives it -0.0002, and opponent quality and opponent-adjusted stats remain the only families whose intervals exclude zero. The already-seen 2025 to 2026 folds (-0.0007, interval -0.0053 to +0.0041) played no part. Numbers: `docs/MODEL_REPORT.md`, "Model revision M4.6".
- **Decision:** recommend rejecting family 16. Nothing was applied: no candidate saved, no refit, `approved.json` untouched. The columns stay in the feature table as candidates that no model reads (as D55 did for family 14), so the comparison can be rerun on later data with one command.
- **The transform passed its own checks:** it picks the judged winner in 82.4% of 523 validation decisions (88.6% unanimous, 58.9% split), its confidence rises with the judges' margin, and its lowest-scoring knockout wins are well-known comebacks. So the failure is not a broken measure of performance. The likely reason, untested, is that the model already reads the same in-fight stats per minute and opponent-adjusted (families 3, 4 and 9), and a weighted sum of them adds little a tree model cannot form.
- **Why not adopt anyway, or try sub-sets:** the rule was fixed so that the decision would not be made by looking at results. Trying single columns now (the performance Elo alone, luck alone) would be seven more chances to pass by luck, the multiple-comparisons problem D54 and D63 were written to avoid. If a sub-set is worth testing, it needs its own registration first.
- **Alternatives:** adopting the family for its interpretability (rejected: the model's inputs are judged by validation log loss, ML_REQUIREMENTS "Candidate models"); using the deserved share only as display context for the site or the analyst (possible later, outside the model; not done here).

### D65. A grouped "why" reason names only its strongest component; the text is rendered at publish time
- **Context:** D59 sums inputs that measure the same thing into one reason, and the reason's text showed every part: "the age and experience gap, 12.4 years younger (25.0 vs 37.3) and 19 fewer UFC fights (4 vs 23)" was listed as a reason *for* the younger fighter. The model weighed age toward him and experience slightly against him; the sum pointed his way, so a fan read "favoured for having 19 fewer fights".
- **Decision:** Two reasons have components: age and experience (`age`: age and the age-shape columns; `experience`: UFC fights, cage time, debut) and rating (`rating`: own Elo; `opposition`: opponents' Elo). Reasons are still ranked by their summed contribution, as in D59, but the title and detail show only the component whose summed contribution toward the fighter is largest ("the age gap, 12.4 years younger"; "the opposition faced, past opponents rated 81 points higher"). Ties go to the component's key, and members are summed in name order, so the mirrored bout picks the same component and the mirrored-summary test still holds word for word. Single-component reasons already showed their strongest member and are unchanged.
- **Rendered from stored numbers:** the "why" and the factors are rendered when artifacts are published, from the contributions and as-of values stored with each prediction (`shap_json`, `features_json`). Predictions stay immutable (D53); only their wording is current. Rows made before D59 still have no "why".
- **Alternatives:** splitting the reasons into separate age and experience reasons for ranking (SHAP splits credit between correlated inputs, which is why D59 sums them); dropping a reason whose text looks like a weakness (hides what the model weighs); storing new text with a new prediction row (a wording change is not an input change, and new rows would reset the live record's "latest prediction" for no reason).
- **Costs accepted:** a reason's displayed value can carry less weight than its rank suggests, when both components point the same way. A reason without components can still show a value that reads as a weakness when the model weighs it that way (for example, a "late-round output" factor listed for the fighter with fewer fights past round 2); that is what the model weighs, and it is shown, not hidden.

### D66. M6 artifacts: pydantic schemas, an all-or-nothing gate, and an append-only archive
- **Decision:** `uv run python -m ufc.predict refresh` ends by building, in memory, one `public/bouts/{bout_id}.json` per predicted bout, `public/upcoming.json` and `public/performance.json` under `data/publish/`, and one archive snapshot per event with predicted bouts. Each is validated against a pydantic model (`src/ufc/publish/schemas.py`, `schema_version` 1, unknown fields and non-finite numbers refused) and the M5 card checks run as before. Only if every check passes is anything written: archive snapshots first, then the bout pages, `performance.json`, and `upcoming.json` last, each public file through a temporary file and a rename; then pages of bouts no longer on a card are removed. One failure anywhere writes nothing, and the last good artifacts stay as they were.
- **Archive:** `archive/predictions/{event}/{timestamp}.json` is claimed with an exclusive hard link, so an existing name can never be replaced, and is made read-only. A snapshot holds what the card showed: each bout's prediction ID, model version, creation time, input hash, probabilities, labels and the "why" summary. An event whose content hash (everything but the publish time and the Wikipedia revision) matches its latest snapshot gets no new one, so hourly refreshes do not fill the archive with copies; a publish whose snapshot name already exists, or that would sort before an existing snapshot, is refused whole. The archive is written before the site files: a set is never shown without its evidence.
- **Bout page contents:** fighters, event, weight class, calibrated probabilities, model version and creation time, limited-data labels with reasons, the "why", up to five factors toward each fighter (same templates), a fixed display set of as-of stats from the stored values (per-minute rates are the shrunk ones the model reads, and say so), and each fighter's last five UFC bouts before the event with result, method and the M4.6 deserved-win probability (the D63 transform, fitted on decisions through 2022), labelled as a description of past fights that no prediction reads. `market` is present with null fields, and `fair_moneyline` is the margin-free American price of the calibrated probability (negative above 50%, +100 at exactly 50%), so M12 can fill market odds without a schema change.
- **performance.json:** the backtest section is copied from the evaluation record of the candidate whose recipe the approved model uses (its lineage parent for a refit), found by version under `data/reports/`; nothing is recomputed, the record's "already seen" note is carried, and a refit is described as having no held-out test. The era-shift caveat is a fixed sentence filled from the walk-forward record. The live record (D67) is a separate section and is never pooled with the backtest. With no matching evaluation record, `backtest` is null and the reason is given.
- **Alternatives:** validating with hand-written checks only (a schema documents the contract for the frontend and the analyst, and the frontend can be typed from it); writing each file as it is built (a failure halfway leaves a mixed set); one archive file per refresh whether or not anything changed (thousands of identical files, and the meaningful changes become hard to find); archiving after the site files (a crash between the two would show predictions with no evidence); recomputing backtest metrics at publish time (two code paths for the same number).
- **Costs accepted:** the public files are replaced one by one, so a reader can briefly see new bout pages with the old `upcoming.json`; every file on its own is valid, and the order means a link from `upcoming.json` never points at a missing page. A bout page is about 20 kB on the current cards, mostly the input names behind each factor. pydantic is a new dependency (with a compiled core; aarch64 Linux wheels exist).

### D67. The live record: before the first bout, latest prediction, matched by dataset IDs and date
- **Decision:** A prediction is live only if it was created before the event's first bout. Start times are not in the data, so the cut-off is the moment the event's date begins in the furthest-ahead time zone (UTC+14): 10:00 UTC on the day before the event date. Of the predictions created before the cut-off, the latest is scored. If it had been superseded before the cut-off, the bout was off the card at that moment and is "cancelled", not scored. Once the dataset's latest event is on or after the event date, the bout is matched to the completed bout on the same date between the same two fighters, by dataset ID in either order; a provisional fighter matches through the ID it was linked to. A win is scored with log loss, Brier and accuracy from `ufc.models.metrics`, and a calibration table in the backtest's confidence buckets; a draw or no contest is "no result". Other statuses are reported, not scored: `pending` (results not in the dataset yet), `no_live_prediction`, `not_found` (no such bout on that date) and `unlinked` (a provisional fighter never linked). Scores are recomputed from the database on every publish; nothing is stored. Each refresh first links provisional fighters on cards dated today or earlier whose name now resolves with the card rules (D49), because card resolution only links fighters on cards it applies, which are future ones.
- **Alternatives:** the stored `is_live` flag (a prediction made on the event date in UTC can be after the first bout of an event in Asia or Australia); midnight UTC on the event date (the same problem for early-start events); a start time from the odds feed (not matched to bouts until M12; this rule can be tightened then); the earliest prediction (not what the card showed when the bouts began); matching by name (rejected in D17).
- **Why:** The live record is the only out-of-sample evidence for a refit (D47), so it must not include anything made after a bout could have started. The cut-off is conservative by design: a prediction made in the 14 hours before midnight UTC of the event date does not count even when the event starts late in the day; a missed live prediction costs a sample, a counted late one would cost the record its meaning.
- **Costs accepted:** bouts added or changed in the last day before an event are often not in the live record. A Wikipedia date that differs from the dataset's date leaves the bout `not_found` rather than guessed; it is listed so that a person can check it. Bouts predicted before this entry are scored from the database rows, which were never edited; they have no archive snapshot, since the archive starts with M6.
